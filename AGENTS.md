# Repository engineering rules

These rules apply to the entire repository. Read `instructions.md`, `CURRENT_PHASE.md`, and relevant docs before changing code.

- Start at `CURRENT_PHASE.md` and implement one phase at a time. Future phases are architectural context until their turn. After each phase passes its required validation, update progress/architecture docs and the phase selector, commit and push to GitHub, then continue automatically. A failed validation or push blocks advancement. After Phase 16, mark the roadmap complete; do not invent phases. Respect later user pause/scope instructions.
- Inspect existing work first. Preserve correct code, keep changes coherent, and never weaken tests or security controls to obtain a passing check.
- Use a modular Django monolith and feature-oriented Next.js App Router frontend. Do not introduce microservices, Kafka, Kubernetes, multiple databases, or broad event sourcing without a demonstrated later requirement.
- Keep business workflows in explicit services, complex reads in selectors, and request validation in explicit serializers. Avoid fat views, serializers, model saves, and signal chains.
- Django is the authentication and authorization authority. Browser guards provide UX only. Default API permission is `DenyAll`; every new view must choose its policy deliberately.
- Preserve the initial `accounts.User` UUID/email model and migration. Email is trimmed and lowercased in full; the database rejects noncanonical/empty and duplicate values. Do not migrate to Django's built-in user or use username login.
- Browser authentication must use server-side Django sessions, HttpOnly cookies, Secure cookies and HTTPS in production, SameSite, CSRF on every unsafe browser operation, session rotation on login, and invalidation on logout. Never store credentials/tokens in localStorage or sessionStorage.
- DRF session authentication alone does not protect anonymous login requests from CSRF. Phase 1 must explicitly enforce CSRF on login and test the real development proxy.
- Django `is_superuser` is infrastructure break-glass only. Application platform administrators use explicit roles/capabilities; platform access must not implicitly bypass seller API isolation.
- Seller is the tenant. Access comes through SellerMembership, never `User.seller_id` or `is_seller`. Validate active membership and capabilities on each operation and context change.
- Scope reads, writes, and related-object resolution to the authorized seller centrally. Never fetch an unscoped browser-supplied ID in seller services. Test cross-tenant read, enumeration, mutation, and foreign-key attacks for every seller feature.
- Use UUID public identifiers for business entities, explicit API fields, bounded pagination, allowlisted filtering/ordering and content types. Do not expose model fields automatically or permit mass assignment of system fields.
- PostgreSQL is authoritative, including in tests. Use foreign keys, constraints, indexes, transactions, and row locks for critical invariants and concurrent workflows. Never substitute SQLite to get tests to pass.
- Use Decimal for money and snapshot prices, currency, discounts, taxes, commissions, and totals at the event. Historical financial records are append-oriented; corrections create compensating entries.
- Inventory requires an attributable transaction ledger, not a stock field alone. Orders split into Order and SellerOrder; sellers see only their portion. State transitions require explicit backend actions.
- Security/business-sensitive operations must eventually write append-only audit records. Never log passwords, hashes, session/CSRF cookies, authorization headers, bank details, or secret configuration.
- Generate local secrets with `pnpm setup:env`; never commit `.env`, credentials, keys, or tokens. Missing/placeholder production configuration must fail closed. Do not trust proxy headers without a controlled ingress.
- Uploads must use generated names, size/type allowlists, private storage outside executable paths, and later scanning. Access storage through a vendor-neutral S3-compatible boundary; no MinIO coupling.
- Celery is deferred until an authorized async workflow needs it. Enqueue after commit, with retry/idempotency policy; evaluate an outbox when critical delivery requires it.
- Verify official stable/support status before adding dependencies; explain choices in `docs/stack.md`, pin direct versions, and update lockfiles. Prefer framework capabilities; defer TanStack, form libraries, storage and worker dependencies until used.
- Run `pnpm check` against PostgreSQL. Validate Compose with `docker compose --env-file .env -f infra/compose.yaml config --quiet`; never print expanded secrets. Add meaningful positive and negative tests in each phase.
- Keep `docs/architecture.md`, `security.md`, `authorization.md`, `data-model.md`, `testing.md`, `deployment.md`, `stack.md`, and `progress.md` accurate. Record persistent decisions here or in those docs.
- `GET /api/v1/health` and web `/health` are liveness endpoints, not readiness. Auth, seller access, onboarding/settings/documents and explicit platform seller management are enabled. Every future view must deliberately choose its policy. OpenAPI is generated offline. Django admin is not enabled.
- Login CSRF is explicitly enforced for anonymous and authenticated unsafe browser requests. Keep the Next.js same-origin proxy, cookie/token rotation, axes tests and forwarding-header spoof tests when auth code changes.
- django-axes stores normalized account identifiers, remote IPs and request metadata for temporary lockouts. Keep reverse-proxy IP trust disabled until a reviewed ingress contract exists. Do not enable axes' admin or log raw attempt data.
- Platform access is an explicit user->role->capability grant. `SUPER_ADMIN` has explicit access, seller read/manage, document read/review and audit-read capabilities; role names and `is_superuser` never grant authority. Bootstrap grants are infrastructure-only and security-event audited.
- `SecurityEvent` is append-only in PostgreSQL through a trigger. Store UUID actor snapshots instead of cascading user foreign keys; hash unknown login identifiers with Django's key so raw submitted email is not retained there.
- Seller requests select context with one UUID `X-Seller-ID` header, revalidated against current active user/membership, seller availability and capability on every operation. Do not persist authority in the session or treat a prior context response as an authorization token. Separate tabs can use separate sellers safely.
- Active memberships can discover pending/active sellers; suspended, rejected and closed sellers are invisible through seller access APIs. Service/query guards require an ACTIVE seller by default; only explicit onboarding/context views may opt into pending access. Platform inspection requires `platform.sellers.read`; lifecycle, document and audit commands require their separate capabilities through `/api/v1/admin/*`.
- System seller roles have no seller; custom roles belong to exactly one seller. PostgreSQL triggers reject foreign-tenant membership roles and changing role/membership identity. Do not remove these constraints or move an existing membership/role between tenants.
- `authorize_role_assignment` is a delegation guard, not a membership mutation workflow. Future staff services must revalidate it inside their transaction, lock relevant memberships/roles, preserve the last owner, and audit changes. Delegated permissions must be a subset of the actor's permissions; OWNER is additionally protected by structural `is_owner` and `seller.ownership.manage` checks.
- `tenant_queryset` filters existing seller-owned rows for reads, related-object resolution and bounded update/delete selection. Queryset `.create()` does not inherit filters: creation services must assign seller from verified access, reject caller-owned system fields, and never allow tenant reassignment.
- Frontend requests go through `apps/web/lib/api/client.ts`: same-origin `/api/v1/*`, cookies included, no cache/redirect following, fresh CSRF before unsafe actions, explicit seller headers and runtime response validation. Never replace HTTP/API errors with success or keep credentials in browser storage.
- Frontend auth and seller context are in-memory UX state. Revalidate admin/seller access against Django; abort/discard stale queries on user, seller or route changes. Client guards cannot protect confidential Server Component/RSC output: any future server-side data load must authenticate/authorize through Django before sending data to the browser.
- The basic admin primitives use semantic HTML and native dialog focus/cancel behavior. Keep advanced table/form dependencies deferred until real usage justifies them. Money display consumes decimal strings, preserves precision using BigInt grouping and never converts amounts to floating point; dates use explicit locale/timezone.
- Seller onboarding creates the pending seller, profile/settings, active OWNER membership and audit/history atomically. Legal name and currency are fixed through seller settings. Registered address freezes after document verification. Approval/reactivation requires a verified unexpired registration and registered address; seller members cannot perform platform review of their own seller, even with platform capabilities.
- Mutation lock order is active actor User; platform grant/role/link rows where needed; Seller; seller membership/role/link rows where needed; child resources. Revalidate after locking and coordinate future staff/grant workflows with this order. Business change and audit/history must commit together.
- Verification uses named private Django storage, generated UUID keys, bounded/re-encoded JPEG/PNG scans and authenticated attachment downloads. No public media route or storage URL is exposed. Production requires fail-closed HTTPS S3-compatible configuration and a private bucket. Durable upload commands compensate ordinary failures; process-crash orphans require later reconciliation.
- AuditLog, SellerStatusHistory and submitted document evidence are immutable in PostgreSQL. Corrections submit new evidence. Keep audit diffs safe: lifecycle/review state or changed-field names, never document contents, raw identifiers, private contact values or request bodies. Scanning/retention remain explicit later operational work.
