# Customer auth/account visual review - Phase 42

Only the existing shared sign-in and customer account functionality is redesigned. Signup, password reset/recovery, email verification delivery and saved items do not exist in the current contract and are not fabricated. Work is isolated on `ui-overhaul-phase42-account` from validated Phase 41 `c369935`; the original user worktree and functional roadmap remain untouched. Phase 43 is not started.

## Design and implementation

The login page uses warm customer tokens, shared brand typography and a narrow practical form. It retains the same session login and `/workspaces` destination for customer/seller/platform accounts. Account routes share the existing customer header/footer and compact task navigation. Profile/security are divider-led forms; saved addresses and historical orders are plain, bounded, operational lists rather than marketing cards. Each seller package has its own status, item snapshots and real carrier events. The receipt displays server money/currency exactly and never reconstructs financial history.

Reads have loading/error/retry states that cannot masquerade as empty data. Labels, autocomplete, validation descriptions, password length help and error focus are explicit. Native address/review/return/cancel overlays preserve focus, busy dismissal and keyboard recovery. Backend eligibility remains authoritative. The fixed login destination, per-user/route query lifetimes, explicit write payloads and session refresh preserve the security boundaries described in `architecture.md` and `security.md`.

## Visual critique and iteration

Preliminary 375px and 1440px captures were inspected for login, overview, profile, addresses, orders and detail. The first mobile account layout repeated identity above the task links and pushed the page heading too far down. That identity chrome is now hidden below 1024px, and navigation uses a compact two-column layout. The initial mobile login showed the seller/workspace explanation ahead of the form; it now follows the form, while desktop keeps it beside the form beneath the introduction. Long amounts wrap safely and order history remains an operational purchase list. Warm dividers and controlled widths provide structure without a field of rounded cards. A native profile save also exposed that the operational workspace session guard unmounted the entire account route during identity refresh, losing its accepted-save message. Customer account entries now have their own route group with the same public URLs and customer session UX gate; authorized private form/read children still unmount during a recheck, while static user-bound feedback survives. Seller/admin guards and Django authorization remain unchanged.

Final six-width captures and native flows pass. Final images were directly inspected for sign-in at 375px, overview at 430px, profile at 768px, orders at 1024px, address error at 1440px, detail at 1920px, and long detail/cancellation error at 375px. These confirm the revised mobile ordering/navigation, tablet form widths, desktop package/receipt composition, long-value wrapping and readable native error dialogs. Automated metrics cover every retained capture: no horizontal overflow, duplicate IDs or page errors, one main/primary heading, native controls at least 16px and unchanged operational palette. The visible Next development indicator belongs to the development preview. Actual anonymous reads and intercepted synthetic account data are reported separately; actual evidence is not an authenticated customer acceptance test.

## Acceptance limits and separate debt

The browser fixtures do not provision real customers or mutate Django profiles, addresses, orders, reviews or returns. The separate existing auth smoke creates/deletes only a disposable local account and intentionally retains immutable security events. Production live authenticated acceptance, assistive technology, touch/zoom and Firefox/Safari-compatible visual/performance acceptance remain pending. No production launch or roadmap-wide visual completion is claimed.

The inherited cart HTTP 308/proxy issue, backend placement currency/idempotency and guest payment reload recovery remain outside this account UI phase. Current backend email changes preserve the verification flag without reauthentication or a general profile-change audit; correcting that assurance requires authorized backend work. Review/return flags are coarse status hints; actual eligibility/duplicate checks remain backend responsibilities. Request abort is not rollback, and uncertain non-idempotent commands may need a read/reconciliation before deliberate retry. Signup/reset/verification delivery and saved items remain unsupported.
